# Ceryx v1.0 Phase 5 - TG16 云端中继可行性评估

更新日期：2026-06-06  
评估对象：Ceryx 跨网络（Internet）控制链路  
结论状态：已评估，建议先做最小 PoC，再决定最终产品化路径

## 1. 结论摘要

Ceryx 当前已经具备稳定的 LAN 内 WebRTC 远控链路。跨网络场景的真正难点不是视图或输入协议，而是：

- NAT 穿透成功率
- 中继延迟
- 安全与隐私边界
- 运营成本与用户安装摩擦

综合当前代码形态和产品目标，**TG16 的最小 PoC 建议采用方案 A：自建 STUN/TURN + 自建信令**。原因是它最接近现有架构，能最大程度暴露真实网络问题，并且不引入额外客户端安装依赖。

如果目标不是验证可行性，而是尽快给少量用户提供可用跨网体验，则可以把 **方案 D（Tailscale / ZeroTier）** 作为过渡方案，但它不适合作为长期产品主路径。

## 2. 需求与约束

### 2.1 典型场景

- 场景 A：iPad（4G / 公共 Wi-Fi）控制家中 NAT 后的 Agent
- 场景 B：Desktop（办公室）控制家中 Agent
- 场景 C：iPad 和 Agent 都处于不同 NAT 之后

### 2.2 核心约束

- 交互延迟要求：Viewport 目标仍应尽量保持在 100ms 级别内
- 视频带宽：720p@30fps 大致在 2-4 Mbps 量级
- 安全要求：媒体流必须保持端到端加密，中继不得解密明文
- 隐私要求：用户内容不应被第三方长期存储
- 成本要求：需要评估自建、托管和第三方虚拟局域网的总拥有成本

## 3. 方案对比

### 3.1 方案 A：自建 STUN/TURN + 自建信令

组成：

- coturn 负责 STUN/TURN
- WebSocket 信令服务负责 SDP / ICE 协调
- Agent 与控制端继续使用现有 WebRTC 轨道

优点：

- 控制力最强，协议和部署完全可控
- 与当前 LAN WebRTC 架构最接近，迁移最自然
- 可保留端到端加密，TURN 只做转发

缺点：

- 需要运维
- TURN 带宽成本会随着使用量线性增长
- 服务器位置会直接影响延迟

适用结论：

- **最适合 PoC**
- 也是长期自建产品路径的基线方案

### 3.2 方案 B：WebRTC + 公共 STUN + 自建信令

组成：

- 公共 STUN 提供 NAT 探测
- 自建轻量信令服务协调连接
- TURN 只在穿透失败时启用

优点：

- 运维成本低
- 上线门槛低于 A
- 对早期用户友好

缺点：

- 公共 STUN 的可靠性与策略不完全可控
- 失败场景仍然需要 TURN 兜底

适用结论：

- 适合低成本试运行
- 不如 A 适合作为严格 PoC，因为它把核心失败点拆散了

### 3.3 方案 C：Cloudflare TURN + Workers 信令

组成：

- Cloudflare Workers 承担信令
- Cloudflare Realtime TURN 提供中继

优点：

- 基础设施运维最轻
- 全球边缘节点有利于降低部分跨地域延迟
- 官方 TURN 文档说明该链路仍保持 WebRTC / DTLS 的端到端加密语义

缺点：

- 平台锁定更强
- 计费与产品边界依赖供应商策略
- 需要把控制面抽象得更清楚，避免未来迁移困难

适用结论：

- 适合作为后续商业化备选
- 不适合作为当前第一版 PoC

### 3.4 方案 D：Tailscale / ZeroTier 集成

组成：

- 让用户安装虚拟组网软件
- Ceryx 检测到虚拟网地址后直接通信

优点：

- 开发最省
- 安全和穿透问题主要由第三方方案解决
- 适合内部验证和早期极小规模使用

缺点：

- 用户额外安装和配置成本高
- 体验不够原生
- 不符合 Ceryx 想要的“一体化远控”方向

适用结论：

- 只能作为过渡方案或企业内训方案
- 不建议作为长期产品形态

## 4. 当前可行性判断

从现有仓库能力看，Ceryx 已经具备：

- WebRTC capture / signaling 的基础代码
- 双端控制端的状态管理与质量统计
- 设备配对、token、权限、诊断链路

因此 TG16 的关键问题不是“能不能做”，而是“以什么代价做、先验证哪条路径”。

我的判断是：

1. **先做方案 A 的最小 PoC**
2. 用真实 NAT 场景测 P2P 成功率与 TURN 回退性能
3. 再决定最终产品路径是继续自建、切换托管、还是保留第三方虚拟组网做兼容方案

## 5. PoC 范围

TG16 的最小 PoC 建议限定为：

- 一个云端信令服务
- 一个 coturn 实例
- Agent 注册 / 心跳 / 连接发现
- iPad 侧通过信令发现 Agent 并建立 WebRTC
- 观测指标：
  - P2P 连接成功率
  - TURN 回退比例
  - 首帧时间
  - 交互延迟
  - 视频稳定性

不建议在 PoC 阶段就做：

- 多租户账号系统
- 内容同步
- 商业化计费
- 完整的控制台云同步

## 6. 决策框架

| 方案 | 开发成本 | 运维成本 | 带宽成本 | 隐私控制 | UX 原生性 | 推荐度 |
| --- | --- | --- | --- | --- | --- | --- |
| A 自建 STUN/TURN + 信令 | 中 | 中-高 | 中-高 | 高 | 高 | **最高（PoC）** |
| B 公共 STUN + 自建信令 | 低 | 低 | 低-中 | 中-高 | 高 | 中 |
| C Cloudflare TURN + Workers | 低 | 低 | 按量 | 中 | 高 | 中 |
| D Tailscale / ZeroTier | 极低 | 低 | 低 | 高 | 低-中 | 低（过渡） |

## 7. 推荐路线

### 7.1 短期

- 按方案 A 做 PoC
- 不改当前 LAN 主路径
- 先验证跨网穿透、TURN 回退、端到端加密和延迟边界

### 7.2 中期

- 若 PoC 结果良好，保留 A 作为自建产品路径
- 若运维压力明显，可评估 C 作为托管中继替代
- 若只是满足小范围协作或企业内部场景，D 可以作为兼容入口

### 7.3 不建议的路线

- 直接把 D 做成主产品方案
- 在没有真实用户数据前，先投入完整商用中继平台
